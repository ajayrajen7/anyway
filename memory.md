- **M3 ✅ Today + session creation.**
  - `server/internal/today/`: `Get(ctx, conn, date)` implements `GET /api/today`. Determines the active phase (latest `phases` row — see decision log), maps the date to a weekday, looks up that phase's day_template, and branches: non-lifting days (`cardio_mobility`/`rest`) return just the day_template info with `session: null` and `slots: []`; lifting days lazily create a `'planned'` session row on first view (`sessions.date` is UNIQUE, so repeat views return the same row, never a duplicate) and return it with its slots — each slot carrying its exercise, its tier-1 swaps, and a `last_actual` (most recent `status='done'` `logged_sets` row for that exercise, across any session — `'skipped'` sets never count, tested explicitly).

The only "missed" handling anywhere is `sweepMissed`, run at the top of every `Get` call: any still-`'planned'` session dated before the requested date flips to `'missed'`. No cron/background job — a single-user PWA that's opened at least once a day doesn't need one, and one wasn't built. Tested directly: view Thursday, don't complete it, view Friday two days later — Friday shows its own full 7-slot template, and only *then* does re-viewing Thursday show it flipped to `'missed'`.

  - **The pushed image is deliberately kept private, not public** — a real security implication thought through, not assumed away: the image embeds `ANYWAY_API_TOKEN` inside the built frontend's JS bundle (§B1's single static bearer token). A *public* image would mean anyone who found the `ghcr.io` package page could `docker pull` it and extract the token directly, without even needing to know the deployed URL first — a materially bigger exposure than "visible in page source to whoever finds the URL," which is the exposure already accepted and flagged for the deployed *site* itself. Keeping the image private closes that specific extra hole; it costs one more piece of one-time setup (a GitHub PAT with `read:packages`, added to Render's account-level registry credentials so it can still pull the private image).
  - **`fly.toml` deleted outright**, not just left unused — an unused hosting config sitting in the repo would read as "this is also supported" when it isn't, and would silently rot out of sync with the actual (Render) setup over time.
  - **Not yet done**: the owner still needs to (1) create the Render service pointed at `ghcr.io/<repo>:latest` with a 1GB disk at `/data` and the registry credential, (2) add `ANYWAY_API_TOKEN` and `RENDER_DEPLOY_HOOK_URL` as GitHub repo secrets, (3) push or manually trigger the workflow. See README.md "Deploying" for the exact steps handed to them. Like the Fly workflow before it, **this is untested against the real Render API** — the same constraint (no reachable network from this session) applies here too; the first real run should be watched.

## Decision log (settled — with rationale)
- **Separate repo from `phayalman`, not a monorepo or shared code.** State-management philosophy is inverted (server-truth-recompute vs. local-truth-offline-first) and the backend language differs entirely (TS vs. Go) — sharing code would mean fighting one architecture or the other continuously. Only the process/doc conventions carried over.
- **No monorepo tooling for `app/` + `server/`.** Two npm/go projects side by side is sufficient at this size.
- **Go toolchain floats to whatever `modernc.org/sqlite` needs** (currently pins `go 1.25.0` in `go.mod` after `go mod tidy`); the sandbox auto-downloaded it via `GOTOOLCHAIN=auto` without issue.
- **Migrations live under `server/internal/db/migrations/`**, not a top-level `migrations/` — `go:embed` cannot reach outside its containing package directory, so the path in `architecture.md` §B3's prose is illustrative, not literal.
- **`db.migrate()` tolerates SQLite's "duplicate column name" error rather than adding a migration-ledger table** (M9) — the only non-idempotent statement in the whole migration set is `logged_sets`'s `ADD COLUMN client_uuid`, so a full applied-migrations tracking table felt like more machinery than one narrow, well-understood exception justifies. Revisit if a second non-idempotent migration ever shows up and this starts feeling fragile.
- **`programme_start_date` is set by `programme.Apply` (`SetIfAbsent`), not by a dedicated settings endpoint** (M9) — there's no UI or API for setting it any other way, matching `prd.md` §A4's own "set once at seed time." If a real Settings screen (§A3) ever needs to *change* the programme start date (e.g. a redo), that's new, deliberate scope, not something to bolt on quietly.
- **Weigh-in's blind-entry stepper shows the live value while adjusting, hides it forever after Save** (M9) — see the M9 memory entry above for the full reasoning; recorded here as settled so it isn't relitigated as an ambiguity later.
- **The Vault defaults to locked, not unlocked, when `programme_start_date` is absent** (M9) — the conservative direction on purpose; see the M9 memory entry.
- **`GET /api/export` gates `weigh_ins` on the same Vault check as `GET /api/weigh-ins`** (M10) — an extension of M9's reasoning to a second route, not a separate spec requirement; see the M10 memory entry.
- **The nightly backup is a plain stdlib goroutine loop, no cron library** (M10) — one daily job for a single-user server doesn't need more than `time.Date`/`time.After`.
- **Hosting is Fly.io, frontend and backend deploy as one binary** (post-M10) — asked and confirmed with the owner; see the memory entry above for the full reasoning and the redirect bug caught while building it.
