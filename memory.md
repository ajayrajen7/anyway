- **M3 ✅ Today + session creation.**
  - `server/internal/today/`: `Get(ctx, conn, date)` implements `GET /api/today`. Determines the active phase (latest `phases` row — see decision log), maps the date to a weekday, looks up that phase's day_template, and branches: non-lifting days (`cardio_mobility`/`rest`) return just the day_template info with `session: null` and `slots: []`; lifting days lazily create a `'planned'` session row on first view (`sessions.date` is UNIQUE, so repeat views return the same row, never a duplicate) and return it with its slots — each slot carrying its exercise, its tier-1 swaps, and a `last_actual` (most recent `status='done'` `logged_sets` row for that exercise, across any session — `'skipped'` sets never count, tested explicitly).

No cron/background job — a single-user PWA that's opened at least once a day doesn't need one, and one wasn't built. Tested directly: view Thursday, don't complete it, view Friday two days later — Friday shows its own full 7-slot template, and only *then* does re-viewing Thursday show it flipped to `'missed'`.

- **Real bug, reported live and fixed: swipe-to-skip was firing on ordinary vertical scrolling, silently discarding real data.** Owner ran an actual session on a real phone (via the deployed Railway URL), entered weight/reps for every set, tapped Finish — the summary came back "0 sets done, 6 sets skipped, 0 kg total volume." Root cause, found by reading `SetRow`'s gesture handler (`SessionExercise.tsx`) alongside `isSwipeLeft` (`session.ts`): the swipe-left-to-skip check only ever compared horizontal distance (`deltaX <= -80px`) and never looked at vertical movement at all — so scrolling down the page with a pending set row under your thumb, if the touch drifted even modestly sideways over the course of the scroll (very easy on a real screen, much harder to reproduce with a mouse in dev), registered as an intentional left-swipe and skipped that set, discarding whatever had been entered for it. This is the standard swipe-vs-scroll disambiguation bug — the original implementation (M4) never guarded against it because it was never exercised on a real touchscreen before this session.
  - **Fix**: `isSwipeLeft(deltaX, deltaY = 0)` now also requires the horizontal movement to *dominate* the vertical (`Math.abs(deltaX) > Math.abs(deltaY)`) — a real swipe passes, a scroll (even a diagonal one) doesn't. `deltaY` defaults to `0` so it's backward-compatible with any caller that only ever tracked X. `SetRow` now tracks `{x, y}` on `pointerdown` (was X-only) and also resets on `pointercancel` (a defensive addition — the browser taking over for native scrolling can cancel a pointer sequence instead of delivering a normal `pointerup`).
  - **This was genuinely undiscoverable without a real device**: mouse-driven interaction in dev/tests never produces the "mostly-vertical-but-somewhat-diagonal" drag a real thumb does, so every prior smoke test (M4's own, and this session's own manual walkthroughs) exercised swipe-skip only as a deliberate, clean horizontal gesture. Worth remembering for anything else in this app that reads raw pointer coordinates — same class of gap as the CORS bug from the first real end-to-end run (post-M10 memory entry): `npm test` passing was never sufficient evidence for real-device touch behavior.
  - Tests: 2 new `session.test.ts` cases (a vertical-dominant "scroll" at the same X threshold correctly returns false in both scroll directions; a real horizontal swipe with only incidental vertical movement still returns true). The existing `SessionExercise.test.tsx` swipe-skip test needed no change (it never set `clientY`, so `deltaY` was already `0`, which trivially satisfies the new dominance check).

- **Real bug found and fixed: deploys weren't actually reaching the owner's open tab, even after Railway had rebuilt.** Across several of this session's own deploys, the owner reported still seeing old UI (a checkbox instead of the new stepper, a missing Protein row) well after a push. Root cause: `vite.config.ts`'s `registerType: 'autoUpdate'` already generates a service worker that calls `skipWaiting`+`clientsClaim` (confirmed by inspecting the built `dist/sw.js` directly) — so a new deploy *does* activate in the background the next time the browser fetches `sw.js` — but nothing in `main.tsx` ever reloaded the already-open tab once that happened, which is the standard missing half of this Workbox pattern. The old cached HTML/JS just kept running silently until the tab was closed and reopened (or refreshed twice, by luck).
  - **Fix**: `main.tsx` now listens for `navigator.serviceWorker.oncontrollerchange` and reloads the page once, guarded against firing twice. This is a one-time architectural fix, not a one-off patch — every future deploy should now reach an already-open tab with at most one reload, instead of needing the owner to manually hard-refresh or reopen the app.
  - **This fix itself needs one manual hard-refresh (or reopen) to take effect the first time** — it can't retroactively update a tab that's already running the old `main.tsx` without the listener. Told the owner this directly rather than letting the same confusion repeat once more.

## Decision log (settled — with rationale)
- **Separate repo from `phayalman`, not a monorepo or shared code.** State-management philosophy is inverted (server-truth-recompute vs. local-truth-offline-first) and the backend language differs entirely (TS vs. Go) — sharing code would mean fighting one architecture or the other continuously. Only the process/doc conventions carried over.
- **No monorepo tooling for `app/` + `server/`.** Two npm/go projects side by side is sufficient at this size.
- **Go toolchain floats to whatever `modernc.org/sqlite` needs** (currently pins `go 1.25.0` in `go.mod` after `go mod tidy`); the sandbox auto-downloaded it via `GOTOOLCHAIN=auto` without issue.
- **Migrations live under `server/internal/db/migrations/`**, not a top-level `migrations/` — `go:embed` cannot reach outside its containing package directory, so the path in `architecture.md` §B3's prose is illustrative, not literal.
- **`db.migrate()` tolerates SQLite's "duplicate column name" error rather than adding a migration-ledger table** (M9) — the only non-idempotent statement in the whole migration set is `logged_sets`'s `ADD COLUMN client_uuid`, so a full applied-migrations tracking table felt like more machinery than one narrow, well-understood exception justifies. Revisit if a second non-idempotent migration ever shows up and this starts feeling fragile.
- **`programme_start_date` is set by `programme.Apply` (`SetIfAbsent`), not by a dedicated settings endpoint** (M9) — there's no UI or API for setting it any other way, matching `prd.md` §A4's own "set once at seed time." If a real Settings screen (§A3) ever needs to *change* the programme start date (e.g. a redo), that's new, deliberate scope, not something to bolt on quietly.
- **Weigh-in's blind-entry stepper shows the live value while adjusting, hides it forever after Save** (M9) — see the M9 memory entry above for the full reasoning; recorded here as settled so it isn't relitigated as an ambiguity later.
- **The Vault defaults to locked, not unlocked, when `programme_start_date` is absent** (M9) — the conservative direction on purpose; see the M9 memory entry.
- **`GET /api/export` gates `weigh_ins` on the same Vault check as `GET /api/weigh-ins`** (M10) — an extension of M9's reasoning to a second route, not a separate spec requirement; see the M10 memory entry.
- **The nightly backup is a plain stdlib goroutine loop, no cron library** (M10) — one daily job for a single-user server doesn't need more than `time.Date`/`time.After`.
- **Hosting is Railway (via Fly.io, then Render), frontend and backend deploy as one binary** (post-M10) — asked and confirmed with the owner at each pivot; see the memory entries above for the full reasoning, the redirect bug caught while building the embedded-serving approach, and why the token moved from a build-time bake to a runtime injection.
- **Free tier is not usable for this app on any platform** (post-M10) — no persistent disk = the 6-month training log gets wiped on every restart. Confirmed and agreed with the owner rather than silently deployed either way.
- **Weight tracking and the Vault are removed entirely, not hidden** (M11) — asked and confirmed; see the M11 memory entry for the full reasoning and everything it touched.
- **Steps is a manual count (`steps_logs`), not a hit/miss like protein** (M11) — asked and confirmed.
- **"Delete an exercise" is session-local and never synced, same as swap/add** (M11) — asked and confirmed; a new `SessionOverlay.removed` field, not a variant of Skip.
- **Week Plan's day grading is day-appropriate (lifting/cardio_mobility/rest each have a different "3"), and a rest day is 2-of-2, not 3-with-one-free** (M11) — asked and confirmed, then reasoned further on the rest-day case specifically (see the M11 memory entry).
- **The old single Week View is permanently split into Coverage + Week Plan tabs, and the old single Session Runner is permanently split into an exercise list + a single-exercise screen** (M11) — not asked as a yes/no (the owner's own numbered requirements specified this shape directly), but logged here as settled since it supersedes old architecture.md §B6.5's "never split /week into tabs" rule.
- **Real-time exercise creation is Option A: one new server endpoint, LLM-drafted-then-validated, inserted into the shared library — not a client-side LLM call, not a queued/deferred design** (M12) — asked and confirmed; see the M12 memory entry and architecture.md §B2's amendment for the full reasoning.
- **`ANTHROPIC_API_KEY` / Claude Haiku 4.5 is a new, permanent backend dependency, optional at runtime** (M12) — asked and confirmed (owner: "any cheap one would do"); the server runs fine with no key set, just with that one endpoint disabled.
